# Отчёт по этапу 5 «Инспекция кода модулей проекта»

**Курсовой проект:** Система управления задачами проекта
**Стек:** C# / .NET 10, Git, xUnit
**Рабочая ветка:** `feature/stage-5-code-inspection`

## 1. Цель работы
Провести формализованную инспекцию исходного кода системы управления задачами, выявить архитектурные и логические недочеты, предложить корректирующие действия и подтвердить результаты инструментальными проверками.

## 2. Таблица замечаний

| № | Место | Проблема | Риск | Рекомендация | Статус |
|---|-------|----------|------|--------------|--------|
| 1 | `TaskService.cs`, `UserService.cs` | В сервисах используется обычный in-memory список/словарь без синхронизации. | Параллельные запросы могут привести к состоянию гонки (Race Condition) при одновременном создании задач. | Для прототипа зафиксировать как ограничение; в будущем перейти на БД или использовать `ConcurrentDictionary`. | Принято как ограничение |
| 2 | `TaskService.cs`, метод `CreateTaskAsync` | В метод не передается `CancellationToken` (или не вызывается `ThrowIfCancellationRequested`). | Невозможность отменить операцию, если клиент отключился или сервер перегружен. | Добавить параметр `CancellationToken cancellationToken = default` и вызывать проверку отмены. | Требует доработки |
| 3 | `TaskService.cs`, метод `AssignUserAsync` | Проверка `request == null` есть (исправлено на этапе 4), но нет валидации полей `UserId` и `TaskId` (пустые `Guid`). | Возможна передача пустых идентификаторов, что приведет к ошибкам логики в `UserService`. | Добавить проверку `if (request.UserId == Guid.Empty)` и возвращать `INVALID_REQUEST`. | Открыто |
| 4 | `TaskService.cs`, логирование | При ошибке валидации выбрасывается `LogWarning`, но детали ошибки не возвращаются клиенту в виде структурированного ответа. | Клиент не понимает, почему именно запрос отклонен (плохой UX). | Внедрить единый формат ответа об ошибке (ErrorCode + Message). | Открыто |
| 5 | `tests/TaskManagement.UnitTests` | Класс `TaskServiceTests.cs` тестирует только счастливые пути и пару негативных (null, пустой Guid). Нет тестов на `AssignUserAsync` с несуществующим пользователем. | Возможны регрессии при изменении логики `UserService`, которые не заметят тесты `TaskService`. | Добавить мок-тесты на `AssignUserAsync`, имитирующие отказ `IUserService` (например, `Success = false`). | Требует доработки |
| 6 | `tests/TaskManagement.UnitTests/...` | Ошибки форматирования (ENDOFLINE) и предупреждение компилятора `CS8625` (передача `null`). | Загрязнение истории Git и лишние предупреждения при сборке. | Применить `dotnet format` и использовать оператор `null!` для явной передачи null в тестах. | Исправлено |
| 7 | `src/TaskManagement.Tasks/TaskService.cs` | Отсутствовала проверка на пустой `ProjectId` при создании задачи. | Создание задач, не привязанных к проектам, нарушение целостности данных. | Добавить проверку `if (projectId == Guid.Empty) return false;`. | Исправлено (этап 4) |

## 3. Результаты проверки по 14 критериям методички

| Критерий | Результат инспекции |
| :--- | :--- |
| **Понятность имен** | Классы `TaskService`, `UserService`, методы `CreateTaskAsync`, `AssignUserAsync` и DTO соответствуют стандартам C# (PascalCase, суффикс `Async`). |
| **Ответственность классов** | Принцип SRP соблюден: `TaskService` отвечает за логику задач, `UserService` — за пользователей. Есть четкое разделение через интерфейсы. |
| **Направление зависимостей** | Зависимости направлены к проекту `Contracts` (интерфейсы `ITaskService`, `IUserService`). Циклических ссылок нет. |
| **Дублирование логики** | Существенного дублирования нет. Тестовые данные создаются в каждом тесте отдельно, но для xUnit это нормально. |
| **Обработка `null`** | В `AssignUserAsync` добавлена проверка `if (request == null)`. В `CreateTaskAsync` проверяется `title` через `IsNullOrWhiteSpace`. |
| **Валидация входных данных** | Проверяется `title`, но отсутствует проверка `Guid.Empty` в параметрах назначения исполнителя (`UserId`, `TaskId`). |
| **Обработка исключений** | Вместо выброса исключений используется паттерн Result (возврат `bool` или `AssignUserResult`), что снижает нагрузку на рантайм. |
| **Использование `CancellationToken`** | Присутствует в сигнатурах методов, но фактически не проверяется через `ThrowIfCancellationRequested` внутри `TaskService`. |
| **Конфигурация и секреты** | В проекте нет захардкоженных паролей или строк подключения. Логирование осуществляется через `ILogger`. |
| **Внешние контракты** | Контракты вынесены в отдельный проект `TaskManagement.Contracts`. Используются `record` (`AssignUserResult`) для иммутабельности. |
| **Наличие тестов** | Есть 6 тестов (Unit и Integration), они успешно проходят. Покрытие можно расширить (см. замечание №5). |
| **Мёртвый/закомментированный код** | В проектах `Tasks`, `Users` и `Contracts` мёртвого кода не обнаружено. |
| **Соответствие `.editorconfig`** | После запуска `dotnet format` код полностью соответствует правилам. |
| **Предупреждения компилятора** | После исправления теста сборка проходит с **0 предупреждений** и **0 ошибок**. |

## 4. Инструментальная проверка

В ходе инспекции выполнены следующие команды:
- `dotnet format --verify-no-changes` — код полностью соответствует правилам `.editorconfig` (после автоформатирования).
- `dotnet build` — сборка успешна, **0 предупреждений, 0 ошибок**.
- `dotnet test` — все **6 тестов** пройдены успешно (Сбоев: 0).

## 5. Внесенные исправления
В рамках этапа были устранены замечания форматирования (автоматически через `dotnet format`), а также исправлено предупреждение компилятора `CS8625` в тестах (путем добавления оператора `null!`).

## 6. Оставшиеся риски
Основными рисками текущего прототипа являются:
1. Отсутствие потокобезопасности при работе с коллекциями в памяти.
2. Отсутствие полноценной базы данных (что допустимо для учебного этапа).
3. Неполное покрытие тестами негативных сценариев при назначении исполнителей.
